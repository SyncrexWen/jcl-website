## 0. 先统一术语（后面所有设计都依赖它）

```
赛季 Season      2026 Fall（后续 2027 Spring …）
 └ 赛段 Stage    瑞士轮 / 双败淘汰
    └ 轮次 Round 瑞士轮第3轮 / 胜者组决赛 …
       └ 比赛 Series（"大场"，一个 BO5 或 BO7）
          └ 小场 Game（第 1…7 局，第 7 局为巅峰对决）
```
下文"比赛"= 大场，"小场"= 其中的一局。（KPL 数据口径也是大场/小场。）

## 1. 范围估算：数据到底有多少

按你们的赛制和 16 队推算（**估算，非实际**）：
- 瑞士轮 3 胜/3 负制：共 **33 场比赛**（第 1–5 轮依次 8/8/8/6/3 场），每场 BO5。
- 双败淘汰：**10 场比赛**（胜一 2 + 败一 2 + 败二 2 + 胜决 1 + 败半 1 + 败决 1 + 总决赛 1），每场 BO7。
- 合计约 **43 场比赛、约 190–200 个小场**。

这个量级决定了：**"每个小场录多细"是整个项目最大的成本变量**（见 P0-1）。

## 2. P0：必须你拍板，否则无法设计数据结构

### P0-1　小场数据的"字段清单"与真实来源
HLTV / VLR 这类对阵页的内核是：**比赛头部 → 分图(小场)切换 → 每图的 BP/阵容/记分牌/数据标签页**。VLR 把比赛页拆成 Overview / Performance / Economy / Logs 等标签页，并支持"全场合计 / 按单图"切换，这个结构我们可以直接借鉴。

映射到王者荣耀，每个小场可展示的信息分四档，**越往下录入成本越高**：

| 档位 | 内容 | 单小场录入量 | 全赛事（约195小场） |
|---|---|---|---|
| T0 | 胜负、比分、时长 | 2–3 项 | 很轻 |
| **T1** | + **BP**：双方 ban 序列、10 个 pick、蓝/红方、选手↔英雄对应 | 约 20 项（下拉选择） | 约 4000 格，可做 |
| T2 | + 选手数据：KDA、经济、伤害、承伤、评分、**出装 6 格**、召唤师技能 | 约 100 项 | 约 2 万格，**手录不现实**，除非有批量来源 |
| T3 | + 曲线与事件：经济差曲线、击杀/暴君/主宰时间线 | 视来源 | 通常只有官方数据接口才有 |

- 我看到一份公开的"王者荣耀赛事接口"文档目录，里面的数据类别有：经济曲线、团战伤害、选手装备经济、技能 CD、全局 BP、英雄组合等——这说明**商业赛事能做到 T3，是因为有官方实时接口**；校园赛没有这个条件。（仅作字段参考，我不会也不应该去调用它。）
- **你需要回答**：你们手上"真实游戏资源还在统计整理"，具体是哪种？赛宝的对局详情截图？人工统计表？能稳定拿到的最细字段到哪一档？
- **我的默认建议**：网站**按 T3 的结构设计页面，但每一档都允许缺失**，页面自动降级（没有 T2 就只显示 BP；没有 BP 就只显示比分）。**赛事全量目标定在 T1，重点场次（淘汰赛、总决赛）争取 T2**。Demo 里用模拟数据把 T0/T1/T2/T3 四种状态各展示一遍。

### P0-2　赛制要"写死"还是"可配置"（多赛季的核心）
你说后续赛季可能换（2027 Spring / Fall）。如果把"瑞士轮 16 进 8 + 8 队双败"写死在代码里，下个赛季就得重写。

- **我的默认建议**：把赛季结构做成**配置文件**：
  - `season.yml` 声明：赛季名、当前状态、使用的版本补丁、各赛段的类型与参数。
  - 支持 3 种赛段类型：**瑞士轮**（N 胜晋级/淘汰、BO 几）、**双败淘汰**、**单败淘汰**；循环赛可后加。
  - **晋级通路图由配置驱动**：对阵树的每个席位声明来源，例如 `胜者组一轮-1 的败者`、`瑞士轮第 5 名`。你文档里的"对阵总表"正好就是这张配置。这样图、对阵占位符（"待定：胜者组第一轮胜者"）、自动晋级都由同一份数据产生。
- **你需要回答**：下个赛季最可能变的是什么？（队伍数 / BO 几 / 是否保留瑞士轮 / 是否新增阶段）——用来决定要抽象到什么程度，避免过度设计。

### P0-3　"小场数据"怎么录入（非程序员约束的最难点）
新闻、公告好办；**一场 BO7 的 BP + 数据**才是对不会编程的人最难的地方。三种路线：

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. Excel 模板 | 每赛季一个工作簿：teams / series / games / picks_bans / player_stats 多张平表（靠 ID 关联）。传到仓库后构建时自动转换并校验 | 同学们最熟；批量粘贴/复制友好 | 要写模板、校验提示要做好 |
| B. 图形化后台（Pages CMS 等） | 浏览器表单，嵌套录入"比赛→小场→选手" | 体验像填问卷，英雄从下拉选 | 依赖 GitHub 登录；嵌套深了表单会很长；国内访问 GitHub 不稳 |
| C. 自建录入页 | 我写一个本地网页，选英雄头像点选录入，导出文件 | 体验最好（BP 点选） | 工作量大，二期再说 |

- **我的默认建议**：**Demo 先用 A 的数据格式（平表 + ID），内部转 JSON**；英雄/装备录入一律"填 ID 或从列表选"，不手打名字；校验脚本负责查错（见 P1-5）。C 作为二期加分项。
- **你需要回答**：谁来录？他们平时用 Excel/WPS 吗？

## 3. P1：我可以按默认推进，你有意见再改

### P1-1　技术选型更新：Astro（静态生成）取代我上一版的"零构建"
**这是对上一版报告的修订**，原因是你新增了需求：
- 多赛季 + 每场比赛一个页面 + 嵌套数据 + 新闻与比赛互相关联，用手写 JS 在浏览器里拼会越来越乱；
- Astro 的内容集合（Content Collections）自带**数据结构校验**，字段缺失/类型错误构建时就报错，正好充当"录入检查员"；
- 每场比赛生成独立静态页，URL 干净、加载快；
- Cloudflare 能直接从 Git 仓库自动构建，**构建工具不再是维护者的负担**。
- 代价：需要 Git 仓库（GitHub 即可）和我来搭一次工程。录入者只改数据文件/Excel/Markdown。

**Cloudflare 现状（需注意）**：调研显示 Cloudflare 的静态托管仍可用 Pages（Git 推送自动构建，免费档每月 500 次构建、静态流量不限），但官方文档已把新项目导向 "Workers + 静态资源"。所以我的做法是：**工程只输出一个纯静态文件夹，不依赖任何 Pages 专属功能**，两种入口都能部署；建站时以 Cloudflare 控制台实际提供的入口为准。
**国内访问提醒**：有社区反馈 Cloudflare 的 workers.dev 域名在大陆被限制，pages.dev 与自有域名也可能间歇不稳。**Demo 阶段先在你的网络里实测**，演示时备一份本地预览作为兜底。

### P1-2　URL 与多赛季结构
```
/                              → 跳转到当前赛季
/2026-fall/                    赛季总览（晋级通路图 + 积分榜 + 近期赛程）
/2026-fall/schedule/           全部赛程
/2026-fall/standings/          瑞士轮积分 + 双败对阵
/2026-fall/match/sw-r1-01/     单场对阵页（#g3 直达第 3 小场）
/2026-fall/teams/ , /teams/xxx/
/2026-fall/news/ , /news/xxx/
/2026-fall/rules/              赛制说明、规则声明（各赛季自带一份，带版本号）
/seasons/                      赛季存档列表
```
- 顶栏有**赛季切换器**；历史赛季自动变为"存档"状态。
- 战队按赛季独立建档（班级阵容每季会变），可选用 `team_key` 串起历史。英雄/装备主表**跨赛季共用**但带"版本补丁"字段（装备会随版本改动）。

### P1-3　单场对阵页的版面（HLTV/VLR 式，适配王者）
```
┌ 头部：赛事·阶段·轮次 | 队徽 A  3 : 1  队徽 B | BO5 · 状态 · 时间 · 直播/回放 ┐
├ 小场切换：[总览] [第1局 A胜] [第2局 B胜] [第3局] … （巅峰对决局特殊标记）      ┤
├ 全局 BP 英雄池条：本系列已被占用的英雄（按小场标注），对双方后续不可选          ┤
├ 选中小场：                                                                    ┤
│   ① BP 看板：蓝/红方，ban 序列与 pick 序列（巅峰对决=盲选、无 ban）           │
│   ② 阵容与记分牌：5 路位置 × 选手 × 英雄 × KDA/经济/伤害/承伤 × 6 格出装       │
│   ③ 经济差曲线 + 关键事件时间线（T3 有才显示）                                │
├ 本场相关报道（来自新闻，按 match_id 关联）                                     ┤
├ 交手记录（本赛季双方历史对局，自动算）  | 上一场/下一场（沿对阵树导航）           ┘
```
- 页面按"有什么数据显示什么"组合模块，降级规则见 P0-1。
- **全局 BP 可视化是 JCL 的特色**（普通联赛没有这种"英雄逐局锁定"），值得做成亮点：每进一局，英雄池条上被锁定的英雄变灰并标注"G2·A队"。
- **自动校验全局 BP**：录入时若某英雄被重复使用（违规），构建会提示——相当于免费的"数据查错"。

### P1-4　晋级通路图（首页/总览页的主图）
- 结构：左 **瑞士轮分组表**（按战绩 3-0、3-1、3-2 / 0-3、1-3、2-3 分栏，显示晋级/淘汰），右 **双败对阵树**，中间用连线表示"瑞士轮第 1–4 名→胜者组、第 5–8 名→败者组"。
- 席位未决时显示占位文案；比赛结束后自动换成队名；每个节点可点击进入对应对阵页。
- 手机上：横向树改为**按轮次分段的卡片列表** + 一张可缩放的完整图。
- 这是全站最需要打磨的单个组件，计划单独出 2 种版式让你选。

### P1-5　录入校验与反馈闭环
- 校验项：ID 是否存在、BO5 比分合法（不能出现 4:2）、同一队同一时间重复比赛、全局 BP 重复英雄、选手不在大名单（规则要求名单外选手不得上场）、每队换人次数超限（瑞士轮 1 次、淘汰赛 2 次）。
- **关键问题**：构建失败时，非程序员看不懂 Cloudflare 日志。方案：校验报告输出成**中文清单**，并在失败时保留上一个可用版本继续对外；通知渠道（邮件/群机器人）二期再接。

### P1-6　新闻/报道模型
- Markdown + 头部信息：`标题 / 日期 / 类型(赛前预告·战报·专访·公告) / 赛季 / 关联比赛 match_id(可多个) / 封面 / 摘要`。
- 对阵页自动列出关联报道；首页"最新战报"自动取最近几篇。
- **加分项（可选）**：没有人工战报时，由数据自动生成一段"战报摘要"（比分、关键小场、MVP、BP 亮点），保证每场比赛页都不空。
- 公告（置顶横幅）与新闻分开，用于"补充通知"（规则里写明补充通知与声明同等效力）。

### P1-7　规则页
- 两份 Word 转 Markdown，各赛季一份，带**版本号与更新日期**；"补充通知"做成规则页下方的时间线。
- 每条规则有锚点，可直接链接（申诉时引用条款很实用）；**迟到处罚做成结构化速查表**（时间档 → 处罚 → 示例）；ban 位数可配置（原文写明"以赛前通知为准"）。

### P1-8　模拟素材与数据（你已确认可用模拟）
- **模拟数据生成器**（固定随机种子，结果可复现）：16 支虚构班级队（标注"演示数据"）→ 按真实瑞士轮逻辑配对并出结果 → 8 强双败结果 → 每个小场生成**符合全局 BP 规则**的 BP 与合理的 KDA/经济/出装。
- Demo 里刻意覆盖多种状态：已结束（T2 完整）、只有 T1、只有 T0、未开始、一场"进行中"；并带一个"2027 Spring（筹备中）"占位演示赛季切换。
- **模拟素材**：英雄用**虚构英雄**（"示例英雄 · 01"+角色色块徽标，按路线配色）、装备用几何图标、队徽用队名首字徽章。
- **替换契约**：英雄/装备/队徽都按 ID 取图（`heroes/{id}.png`）。以后只需把真实图放进文件夹、在主表里填名字即可，页面零改动。真实游戏素材的授权问题到那时再处理。

### P1-9　视觉系统
继承海报的青绿 + 香槟金 + 米白；深色主题；数字用窄体等宽以对齐；手机优先；**对阵页的数据表在手机上要改成"每名选手一张卡片"**，避免横向滚动。首页 Hero 因海报是竖图，会先做"奖杯居右 + 文案居左 + CSS 重绘背景"的方案，等你决定是否提供横版图。
