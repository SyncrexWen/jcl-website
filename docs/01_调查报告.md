## 1. 我们要做什么

**一句话**：为北京大学基础医学院"基础杯（JCL, Ji Chu League）"王者荣耀赛事做一个**官方赛事主页**，作用相当于校园版的 KPL / LPL / VCT 官网：让选手、观众、裁判组随时能查到「赛程、比分、积分榜、对阵图、战队名单、规则、新闻」。

**使用者**
| 角色 | 想要什么 |
|---|---|
| 选手 / 队长 | 我什么时候打、打谁、迟到怎么罚、能不能换人、怎么申诉 |
| 观众（同学、老师） | 现在打到哪了、谁晋级了、看直播/回放、读赛事报道 |
| 赛事组（**网站维护者，多数不会编程**） | 录比分、发公告、写报道、传图片，**不碰代码** |

**核心设计约束（你提出的）**：非程序员也能方便地添加数据条目与内容报道。这是整个技术选型的第一优先级，其次才是"好看"。

**Demo 的范围**：先做一个可运行、可点击、带示例数据的网站原型，用来确定内容结构和视觉风格；不追求上线级别的功能（直播、账号、评论等放到后期）。

## 2. 现有材料盘点

### 2.1 赛制事实（来自《JCL赛制说明》）
- 时间：文档写明 2026.9.28 – 11.1（⚠️ 见 §9 待确认：今天已是 11/6）。
- **第一赛段·瑞士轮**：预计 16 队；5 轮；每场 BO5 全局 BP；三胜晋级；前 8 晋级。排名：大分 → 净胜局 → 相互战绩 → BO1 加赛。
  第 1–4 名进胜者组，第 5–8 名进败者组。
- **第二赛段·双败淘汰**：8 队，BO7 全局 BP，第七局"巅峰对决"（盲选、无 ban）。共 7 个轮次（胜者组一轮 → 败者组一轮 → 败者组二轮 → 胜者组决赛 → 败者组半决赛 → 败者组决赛 → 总决赛），冠亚季殿由对阵表直接决定。
- 全局 BP：同一系列赛里已选用的英雄双方后续都不能再用；ban 仅当局有效。

### 2.2 规则事实（来自《JCL规则声明》）
七大块：参赛资格与名单（5 主力 + ≤4 替补，名单锁定）、迟到处罚（5/10/15 分钟分档，累计处罚，不可抗力顺延）、选手轮换（瑞士轮 1 次/场，淘汰赛 2 次/场）、比赛纪律、掉线重开、申诉（赛后 24 小时内）、附则。
→ 网站上最适合做成**可折叠的规则页 + 一张"迟到处罚速查表"**，而不是让人读一整篇 Word。

## 3. 参考调研：主流游戏赛事官网怎么做

> 方法说明：我检索了 KPL、LoL Esports、VCT(valorantesports.com)、Liquipedia、VLR.gg 等。**搜索工具只能拿到页面摘要，没能逐屏看到这些官网的真实排版**，因此下面的"共性结构"是综合摘要信息 + 对这类站点的通用认识归纳，视觉细节请当作"方向"，不要当作精确复刻。

### 3.1 共性信息架构（几乎所有赛事官网都有）
1. **顶栏导航**：赛程 / 积分榜（或对阵图）/ 战队 / 选手 / 新闻 / 规则（或 Handbook）/ 直播入口。
2. **首页 Hero**：当前赛事主视觉 + 一句话口号 + 主要按钮（看直播 / 看赛程）。
3. **"正在发生"条**：LIVE 比赛、下一场倒计时、今日赛程。这是电竞站点和普通站点最大的区别——**时间驱动**。
4. **赛程页**：按日期分组的比赛卡片：双方队徽、比分、BO 几、状态（未开始/进行中/已结束）、回放链接；可按阶段/队伍筛选。
5. **积分榜 / 对阵图**：联赛用积分表；淘汰赛用树状对阵图。VCT 的 League Handbook 把"赛制说明"单独成页，与我们的《赛制说明》高度对应。
6. **战队页 / 选手页**：队徽、名单、位置、战绩；选手有位置、代表英雄。
7. **新闻 / 公告**：卡片列表 + 文章详情，带标签（赛果、公告、花絮、专访）。
8. **规则 / 手册页**：独立页面，长文可目录导航。
9. **页脚**：主办方、合作方/赞助、联系方式、社交账号（我们对应：基础医学院、公众号二维码）。

### 3.2 几个值得借鉴的具体做法
- **LoL Esports**：Watch 页（赛程 + 积分 + 回放）可开"无剧透模式"，隐藏比分——我们是校园赛，回放/录像是否公开可以后续再定，但"无剧透"是低成本加分项。
- **VCT**：把赛季分成 Kickoff / Stage / Masters 等多个阶段切换；对应我们的「瑞士轮 / 双败淘汰」阶段 Tab。
- **Liquipedia / VLR 类数据站**：信息密度高、表格为王。我们的积分榜、战绩表应当走这种"清晰的表格"风格，而不是花哨图形。
- **KPL 一类国内站点**：战队介绍、选手卡片、周最佳/MVP 类数据奖项是内容重点，赛事热度来自"人"。校园赛里**选手与班级的故事**比数据更有传播力 → 战队页、选手页值得做好。

### 3.3 与我们场景的差异（决定了不能照搬）
| 商业赛事站 | JCL |
|---|---|
| 数据由官方 API 自动喂入 | 没有 API，**全部手工录入**（队伍 16、总场次约 40+30 场，量不大） |
| 有专业摄影、选手形象照 | 素材少，需要"没图也好看"的卡片设计 |
| 要承受高并发 | 只有校内几百人访问，静态页面足够 |
| 有后台开发团队 | 维护者是学生，**零运维** |

→ 结论：**做静态站点 + 手工数据 + 自动计算**，不要引入数据库和服务器。

## 4. 页面规划（站点地图）

```
首页 /
├─ 赛程 /schedule         （全部比赛；按阶段、日期、队伍筛选）
├─ 积分与对阵 /standings
│    ├─ 瑞士轮积分榜（按 战绩分组 3-0 / 2-1 …，自动算排名）
│    └─ 双败淘汰对阵图（树状图，自动按比分推进）
├─ 战队 /teams            → 战队详情 /teams/xxx（名单、战绩、赛程）
├─ 选手 /players          （可选，二期）
├─ 新闻 /news             → 文章详情 /news/xxx
├─ 规则 /rules
│    ├─ 赛制说明
│    └─ 规则声明（迟到/轮换/掉线/申诉 速查）
├─ 报名与通知 /join       （报名入口、赛事群、联系人；赛前阶段是首页主 CTA）
└─ 关于 /about            （主办方、基础医学院、致谢、联系）
```

### 4.1 首页模块（自上而下）
1. **Hero**：奖杯主视觉 + "这次，该我上场！" + JCL 2026 + 当前状态按钮（报名中 / 查看赛程 / 看对阵）。
2. **赛事状态条**：当前阶段（如"瑞士轮 第3轮"）+ 进度条 + 下一场倒计时。
3. **今日/近期赛程**（3–6 张比赛卡）。
4. **最新战报**（3 篇新闻卡片）。
5. **迷你积分榜**（前 8 名）→ 链接完整页。
6. **赛制一图流**：瑞士轮 → 双败 → 冠军，一张流程图让新同学 10 秒看懂。
7. **战队墙**：16 个队徽/班级名。
8. 页脚：主办方、公众号二维码、联系方式。

### 4.2 各页核心内容与数据来源
| 页面 | 关键内容 | 数据来自 |
|---|---|---|
| 赛程 | 比赛卡：阶段/轮次、时间、A vs B、BO、比分、状态、回放链接 | `matches` 表 |
| 瑞士轮积分榜 | 排名、队伍、胜-负、大分、小分(净胜局)、晋级标记 | **由 `matches` 自动计算** |
| 双败对阵图 | 7 个轮次的树状图，胜者自动推进，败者自动落入败者组 | `matches` + 固定对阵规则 |
| 战队页 | 队名、班级、队徽、队长、大名单(主力/替补)、本届战绩与全部比赛 | `teams` + `players` + `matches` |
| 新闻 | 标题、日期、标签、封面、正文（图文） | Markdown 文件 |
| 规则 | 赛制、规则条款、迟到处罚表 | 由两份 Word 转成的 Markdown |

## 5. 数据模型（让"录数据"变成"填表"）

核心原则：**一份数据只录一次**。比分只在 `matches` 里录一遍，积分榜、对阵图、战队战绩全部由程序算出来，不让人手算。

**teams（战队）**：`id`、队名、班级、简称、队徽图、队长、简介、口号
**players（选手）**：`id`、`team_id`、昵称/姓名、位置、是否主力/替补、代表英雄（可选）
**matches（比赛）**：`id`、阶段(swiss/winners/losers/final)、轮次、开赛时间、`team_a`、`team_b`、BO(5/7)、`score_a`、`score_b`、状态(未开始/进行中/已结束)、回放链接、备注
（淘汰赛的"谁打谁"在上游队伍未决时显示为"胜者组第一轮胜者"这类占位符，由对阵规则推出）
**news（新闻）**：标题、日期、标签、封面、摘要、正文
**announcements（置顶公告）**：文字、级别、起止日期（首页顶部横幅用）
**settings（赛事设置）**：赛事名、届次、当前阶段、报名是否开放、公众号二维码、联系人

**自动计算项**
- 瑞士轮：胜-负战绩、大分、净胜局、相互战绩、排名；三胜晋级/三负淘汰标记。
- 双败：根据你文档里的"对阵总表"固定模板，把比赛结果映射成对阵树；并列名次（5–6、7–8）自动标注。
- 战队页：自动汇总该队所有比赛。

## 6. 技术架构：三个候选方案

先说判断标准（按你的要求排序）：
① **非程序员能改内容**　② 好看、可定制（贴合 JCL 视觉）　③ 零运维、免费　④ **校内/国内能稳定访问**　⑤ 将来可扩展

### 方案 A：纯静态 + 数据文件（零构建）★ 推荐用于 Demo
- 用 HTML/CSS/少量 JavaScript 手写页面；数据放在 `data/*.csv`（或 `*.json`）；新闻放 `news/*.md`。
- 页面打开时由 JS 读取数据，**在浏览器里自动计算**积分榜与对阵图。
- 维护者用 **Excel / WPS 打开 CSV 填表**，把文件放回文件夹即可；新闻写 Markdown（和写微信公众号差不多，后面可配图形化编辑器）。
- 优点：没有构建工具、没有依赖；双击就能本地预览；任何静态空间都能托管。
- 缺点：Markdown/CSV 对完全小白仍有一点门槛；本地用 `file://` 打开时浏览器会限制读取数据文件，需要一个一键启动的小脚本（我会提供）。

### 方案 B：静态站生成器（Astro / Eleventy）+ 图形化 CMS（Pages CMS / Decap / Sveltia）
- 内容存 Git 仓库；CMS 给编辑者一个**网页表单后台**（所见即所得写新闻、表格式录比分），每次保存就是一次提交并自动重新发布。
- 调研要点：Pages CMS 只需在仓库放一个 `.pages.yml`，在网页里编辑，每次保存会提交回 GitHub，不需要自己的数据库；也不需要懂 Git。Decap 更成熟，Astro 在 2026 年仍是内容型站点的主流选择。
- 优点：编辑体验最好（像发公众号一样）；有版本历史、可回滚、多人协作。
- 缺点：需要 GitHub 账号体系；**GitHub Pages 在国内访问不稳定**（见 §8）；有一个学习与配置成本。

### 方案 C：现成建站平台（WordPress / 飞书 / 腾讯文档 / 语雀嵌入）
- 优点：最省事。缺点：对阵图、自动积分榜很难做；视觉不可控；与"做一个赛事官网 demo"的目标不符。→ 不推荐，仅作为"公告发布渠道"的补充（公众号本身就是）。

### 推荐路线：**A 起步，保留升级到 B 的路径**
1. **Demo 阶段（现在）**：用方案 A。数据格式与内容目录**按 B 的要求设计**（Markdown + 结构化数据），这样后面接 Pages CMS 只需加一个配置文件、不用返工。
2. **正式上线前**：决定托管位置（§8），再决定是否接入图形化后台。
3. 为"最不会代码的人"提供第三条路：**一个本地"赛事数据录入页"**（admin.html）——表单填写→一键导出新的 CSV/JSON，替换文件即可。可作为二期，不依赖 GitHub。

### 为什么不用数据库/后端
数据量小（几十队/场）、访问量小、更新频率低（每场比赛结束更新一次）；数据库只会增加运维和被攻击面。静态方案对学生团队更安全、更耐久（赛事结束后网站可以永久存档）。

## 8. 部署与访问（需要你拍板的关键一点）

观众主要是北大同学，部分在校内网、部分在校外/手机流量。静态托管选项：

| 选项 | 费用 | 国内访问 | 备注 |
|---|---|---|---|
| GitHub Pages | 免费 | 搜索到的实测与经验帖说明**经常慢或不稳定**，部分区域易被间歇性限制 | 与方案 B 配合最好 |
| Cloudflare Pages | 免费 | 同样有反馈称国内部分省份不稳 | |
| Netlify / Vercel | 免费 | 有帖子称 Netlify 国内较快但**微信内可能打不开**（该帖说法，需实测） | 微信内打开是我们的关键场景 |
| 腾讯 EdgeOne Pages 等国内 CDN 方案 | 有免费额度 | 社区反馈较好 | 绑定自有域名在大陆需要备案 |
| Gitee Pages | — | 有帖子称已下线，自定义域名需备案 | 不建议 |
| 校内服务器 / 学院网站空间 | 免费 | 校内最稳 | 需向学院/信息中心申请，并走学校审批 |

**要点**：网站大概率要从**微信公众号文章链接**进入，所以必须实测"微信内置浏览器能否打开"；面向校外公网发布、绑定域名通常涉及备案。这部分我无法替你判断学校规定，建议你向学院老师确认**"能否用学院/学校的静态空间"**。Demo 阶段先不依赖任何托管，本地即可演示。

## 9. 待确认事项 / 风险

1. **时间线对不上**：文档写赛事时间为 2026.9.28–11.1，而今天是 2026-11-06，海报仍写"季前赛·报名现已开启"。网站该按"赛前（报名期）""进行中""已结束（存档）"哪个状态做 Demo？我建议 Demo 带一个 `settings.stage` 开关，**三种状态首页都能切换展示**。
2. **"季前赛"与"JCL 2026"的关系**：海报标的是"JCL 季前赛"，规则文档是"JCL 全部赛段"。网站命名是否统一为 "JCL 2026"，季前赛作为其中一个赛事分类？
3. **队伍规模**：文档写"预计 16 队"。有真实队伍名单吗？没有的话 Demo 用虚构示例队名（班级名），并明确标注 Demo。
4. **选手隐私**：规则要求实名报名，但网站公开展示选手姓名/班级是否已获本人同意？建议默认只展示**游戏ID**，姓名/班级由队伍自愿。
5. **版权/IP**：网站要用到"王者荣耀"名称、英雄、游戏截图，需关注腾讯对赛事、校园赛事使用游戏素材的授权与规范，以及学院是否有要求标注"非官方/校园赛事"。Demo 内先不放英雄头像与游戏截图，页脚加声明占位。
6. **直播/回放**：有计划放 B 站/视频号直播间吗？有的话首页预留"直播入口"。
7. **规则的两处可核对点**（不影响 Demo，但建议赛事组确认）：
   - 瑞士轮"三胜晋级、三败淘汰、最多 5 轮"，16 队时晋级 8 队与"前 8 名"自洽；但文中又写"5 轮结束后按大分排名"，两种口径在人数不规整时会不一致。网站按"三胜晋级/三败淘汰 + 5 轮上限"实现，请确认。
   - 迟到处罚中的 ban 位数量"以赛前通知为准"，网站把它做成**可配置**而非写死。

## 10. 视觉与交互方向（供你判断）

**关键词**：沉稳、荣誉感、竞技感，但不要网游式的"炫"——毕竟是医学院的赛事，**青绿+金**自带学院气质。

- **配色**：深青绿渐变背景 + 香槟金强调色 + 米白文字（继承海报）。深色主题为主，表格区域保证对比度。
- **字体**：标题用有力量感的黑体/宋体变体（Web 中文字体需考虑加载体积，倾向系统字体 + 一款标题字体子集）；数字用等宽/窄体，利于比分对齐。
- **Hero**：奖杯居右，文案居左，背景光带做缓慢流动（CSS 动画，可关闭）。
- **移动端优先**：入口多来自微信，所有页面先按手机屏设计，再放大到桌面。
- **对阵图**：桌面横向树状图；手机上改成"按轮次分段的卡片列表"，避免要左右滑。
- **没图也好看**：战队无队徽时，自动用队名首字 + 主题色生成徽章。
- **可访问性**：对比度达标、支持键盘访问、尊重"减少动效"。

> 我准备做 **2–3 个首页视觉方向的低保真对比**（不同 Hero 构图与信息密度），由你选定后再进入完整实现。
